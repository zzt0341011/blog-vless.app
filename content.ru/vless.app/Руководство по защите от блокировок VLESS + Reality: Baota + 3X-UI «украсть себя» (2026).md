# Узлы постоянно блокируют TCP? Правильный способ настройки Reality: Baota + 3X-UI «украсть себя» — подробное руководство

В последнее время многие пользователи столкнулись со странной проблемой: сервер пингуется, UDP работает нормально, но все новые TCP-соединения (даже SSH) обрываются. Многие начинают думать, что протокол Reality перестал работать, но это не так — проблема чаще всего кроется в «упрощённом» способе настройки, который не использует маскировочные возможности Reality в полной мере.

![vless-3xui-feng1001.png](https://vless.app/img/vless-3xui-feng1001.png)

В первой половине этого руководства мы пошагово разберём, как с помощью **панели Baota + 3X-UI** построить высомаскировочный узел Reality по методу «украсть себя» (включая схему маршрутизации AI-трафика через резидентный IP). Во второй половине подробно объясним технические принципы каждого шага.

### Шаг 2. Подключение к серверу по SSH

После переустановки системы подключитесь с помощью встроенных инструментов (Terminal на Mac, PowerShell на Windows). Введите следующую команду и нажмите Enter, затем введите пароль (при вводе пароль не отображается).  
Также можно использовать графический SSH-клиент, например [FinalShell](https://www.hostbuf.com/t/988.html).

```bash
ssh root@IP_ВАШЕГО_СЕРВЕРА
```

### Шаг 3. Установка файрвола и панели Baota / aaPanel

1. **Установите файрвол UFW**: в терминале введите `apt install ufw` и подтвердите установку.
2. **Установите панель управления**: можно использовать панель Baota; если неудобно привязывать китайский номер телефона, подойдут альтернативы вроде aaPanel или 1Panel.


### Шаг 4. Установка 3X-UI и временное открытие панели

1. После входа в Baota откройте встроенный терминал и выполните скрипт установки 3X-UI.
2. Поскольку ранее был установлен файрвол, только что установленная панель 3X-UI по умолчанию недоступна. Перейдите на страницу **«Безопасность»** в Baota, временно отключите файрвол (или откройте соответствующий порт), после чего войдите в панель 3X-UI с логином и паролем.

```bash
bash <(curl -Ls https://raw.githubusercontent.com/mhsanaei/3x-ui/master/install.sh)
```

### Шаг 5. Установка окружения для сайта (Nginx, PHP, MySQL)

Вернитесь в **«Магазин приложений»** Baota и быстро установите **Nginx**. Чтобы создать реалистичный маскировочный сайт, также рекомендуется установить **PHP** и **MySQL** (безопасность и сложность растут вместе).

![vless-3xui-feng1004.png](https://vless.app/img/vless-3xui-feng1004.png)

### Шаг 6. Настройка DNS и создание сайта (критические моменты)

1. **Настройте DNS**: рекомендуется использовать отдельный домен верхнего уровня (бесплатные домены второго уровня нежелательны). Добавьте A-запись, указывающую на IP вашего сервера; имя хоста может быть обычным, например `api`.
2. **Отключите прокси (серое облако)**: если используете Cloudflare, **обязательно отключите статус прокси (облако должно быть серым)** и используйте только DNS.
3. **Создайте сайт и получите сертификат**: в разделе «Сайты» Baota добавьте разрешённый домен, запросите бесплатный SSL-сертификат и включите **«Принудительный HTTPS»**.
4. **Замените содержимое страницы**: замените страницу по умолчанию в корне сайта на реальное содержимое или пользовательскую одностраничную страницу.

![vless-3xui-feng1005.png](https://vless.app/img/vless-3xui-feng1005.png)

### Шаг 7. Изменение конфигурации Nginx, чтобы освободить порт 443

Это ядро метода «украсть себя». Перейдите в Baota «Сайты» → нажмите **«Настройки»** нужного сайта → **«Файл конфигурации»**, внесите два изменения и сохраните:

1. **Измените порт прослушивания**: измените исходный порт `443` на `8443` (можно дополнительно ограничить только локальным адресом `127.0.0.1:8443`), освободив стандартный порт 443.
2. **Измените правило принудительного перенаправления**: найдите строку «перенаправлять, если порт не равен 443» (содержит `!= 443`), **уберите восклицательный знак `!` и замените `443` на `80`** (то есть перенаправлять на HTTPS только когда порт равен 80).

> После сохранения сайт временно станет недоступен. Это нормально, потому что порт 443 уже освобождён, но ещё не занят 3X-UI.

![vless-3xui-feng1006.png](https://vless.app/img/vless-3xui-feng1006.png)

### Шаг 8. Создание входящего узла Reality в 3X-UI

Вернитесь в панель 3X-UI, нажмите **«Входящие»** → **«Добавить входящий»** и настройте следующие параметры:

- **Порт**: обязательно `443`
- **Безопасность**: выберите `Reality`
- **Dest**: укажите `127.0.0.1:8443` (должен совпадать с портом в конфигурации Nginx из предыдущего шага)
- **Сканирование и ключи**: нажмите «Сканировать» (появится ошибка сертификата — это нормально, просто подтвердите), затем получите новую пару ключей, создайте её и добавьте клиента

После создания обновите ваш маскировочный сайт. Страница должна снова открываться, а узел — нормально подключаться.

![vless-3xui-feng1007.png](https://vless.app/img/vless-3xui-feng1007.png)

### Шаг 9. Повторное включение файрвола и закрытие лишних портов

Вернитесь на страницу **«Безопасность»** в Baota, снова включите файрвол и массово удалите ненужные открытые порты (20, 21, 888, FTP и т.д.), оставив только необходимые (22, 80, 443 и порт панели Baota).

- Порт панели 3X-UI в обычное время не следует открывать наружу. Временно добавляйте правило разрешения только при необходимости изменения конфигурации и сразу удаляйте его после использования.

## 2. Расширенная настройка: маршрутизация AI-трафика через резидентный IP

Если ваш узел должен использоваться для доступа к AI-сервисам, которые строго относятся к IP дата-центров, можно подключить статический резидентный IP через исходящую маршрутизацию 3X-UI:

1. **Приобретите статический резидентный IP**: помимо США можно рассмотреть Сингапур или Японию (часовой пояс UTC+8 лучше совпадает с привычным режимом использования; перед покупкой убедитесь, что регион есть в списке поддерживаемых целевым AI-сервисом).
2. **Добавьте исходящий SOCKS5**: после получения данных SOCKS5-прокси резидентного IP создайте в разделе **«Исходящие»** 3X-UI новый исходящий протокол `socks` (тег можно назвать `us-home`), заполните адрес, порт, имя пользователя и пароль, проверьте реальную задержку и сохраните.
3. **Настройте специальные правила маршрутизации для AI**: перейдите в **«Маршрутизация»** → **«Правила маршрутизации»**, создайте новое правило, в поле доменов выберите категорию `AI`, укажите исходящий тег на только что созданный резидентный IP и сохраните. Так реализуется схема «только AI-трафик идёт через резидентный IP, остальной трафик — напрямую на сервер», что позволяет балансировать скорость и расход трафика.

## 3. Разбор принципов: зачем всё это усложнять?

### 1. Почему раньше «кража Microsoft/Apple» легко блокировалась?

Механизм Reality заключается в том, что в первом пакете TLS-рукопожатия спрятан секрет: если секрет совпадает — пересылается прокси-трафик; если не совпадает (например, при активном зондировании) — сервер пересылает всё соединение без изменений на целевой сайт.

Раньше для удобства в качестве цели указывали крупные сайты вроде Microsoft или Apple, но у этого было три скрытых риска:

- **Несоответствие личности и адреса**: у сервера IP BandwagonHost в Лос-Анджелесе, а он выдаёт себя за Microsoft. Простая проверка DNS показывает, что IP не принадлежит Microsoft.
- **Неестественная задержка рукопожатия**: при каждом зондировании серверу приходится идти через сеть к удалённому Microsoft и возвращать результат — задержка выглядит неестественно.
- **Превращение в публичный ретранслятор**: если заимствованный целевой сайт стоит за Cloudflare, сервер может стать публичным прыжковым хостом.

При методе **«украсть себя»** домен, DNS, SSL-сертификат и реально работающий сайт находятся на одном и том же сервере. Как бы ни зондировали снаружи, информация полностью согласована, а цель находится на localhost (`127.0.0.1`), поэтому задержка пересылки крайне низкая.

![vless-3xui-feng10091.png](https://vless.app/img/vless-3xui-feng10091.png)

### 2. Раз уж есть настоящий сертификат, почему не использовать классический TLS fallback?

Есть две основные причины:

- **Устранение серверного TLS-отпечатка**: в классических TLS-схемах с зондирующим всегда рукопожатие проводит сама программа Xray, и только после расшифровки происходит fallback на Nginx. Reality вообще не расшифровывает незнакомые соединения — передаёт их Nginx как есть, поэтому зондирующий всё время общается с настоящим сайтом Nginx, полностью устраняя серверный TLS-отпечаток.
- **Минимальные изменения среды сайта**: классический TLS fallback передаёт Nginx открытый текст, требует дополнительного открытого порта и легко конфликтует с принудительным HTTPS в Baota. В схеме Reality Nginx продолжает работать по HTTPS как обычно и просто переносится на локальный порт 8443, не мешая продлению сертификатов и обслуживанию сайта.

![vless-3xui-feng10092.png](https://vless.app/img/vless-3xui-feng10092.png)

### 3. Причины «контринтуитивных» действий

- **Зачем устанавливать PHP/MySQL и делать настоящий сайт?** Если зондирующий откроет ваш домен и увидит только пустую или стандартную страницу, маскировки почти нет. Сайт с нормальным содержимым наименее заметен.
- **Почему обязательно выключать облако Cloudflare?** Reality сам по себе не проходит через CDN. Кроме того, при включённом прокси разрешение домена становится IP Cloudflare, которое снова не совпадает с реальным IP сервера, к которому напрямую подключается клиент.
- **Почему Reality должен занимать 443, а Nginx — переезжать на `127.0.0.1:8443`?** Обычные HTTPS-сайты работают на порту 443; порты, отличные от 443, повышают вероятность блокировки. Ограничение Nginx локальным loopback не позволяет внешним сканерам обнаружить второй такой же сайт на порту 8443.
- **Почему удалять восклицательный знак в конфигурации Nginx?** По умолчанию в Baota правило: «принудительно перенаправлять на HTTPS, если порт не 443». После смены Nginx на 8443 без изменения этого правила возникает бесконечный цикл перенаправлений. Изменение на «перенаправлять только когда порт равен 80» решает проблему.
- **Почему можно игнорировать ошибку сертификата при сканировании?** Сканирование проверяет сертификат вашего домена через `127.0.0.1`, поэтому имя хоста естественно не совпадает. Достаточно, чтобы результат сканирования показывал поддержку TLS 1.3 и ALPN `h2` — это полностью соответствует требованиям Reality.
- **Почему в конце обязательно снова включать файрвол и закрывать лишние порты?** Чем больше портов и панелей управления открыто наружу, тем больше сервер похож на специализированную прокси-машину и тем выше риск брутфорса панели.
